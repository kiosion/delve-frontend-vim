1. INTRODUCTION                              *delve-frontend* *delve_frontend*
                                                        *delve-frontend-intro*

delve-frontend runs and debugs Go tests. It marks each test, subtest and table
case in a `_test.go` file with a sign, runs the test at the cursor with
`go test`, and debugs it with dlv in a tab of its own. It also debugs main
packages, attaches to processes, and connects to headless dlv servers.

The plugin needs Vim 9.1.0142 or later, on macOS or Linux, with Go 1.25 or
later in `PATH`. Debug sessions also need dlv in `PATH`. In Neovim and older
versions of Vim, the plugin does not load and prints no message.

The plugin defines commands and |<Plug>| mappings, and maps no keys. See
|delve-frontend-mappings| for an example.

To disable the plugin, set this in your |vimrc|:
>
	let g:loaded_delve_frontend = 1
<
==============================================================================
2. QUICK START                                     *delve-frontend-quickstart*

The plugin builds its helper the first time you open a `_test.go` file (see
|delve-frontend-setup|). When the build ends, a `▶` sign marks each test.

To run one test, subtest or table case:

1. Move the cursor into the test.
2. Run |:DelveFrontendRunTest|. A results window opens at the bottom and
   shows the output of `go test` with the flags that select the test. When
   the run ends, the signs of the tests that ran show `✓` or `✗`.

To debug it:

1. Move the cursor to a line that the test runs, and run
   |:DelveFrontendToggleBreakpoint|. For a table case, use a line in the
   function that `t.Run` calls. A `●` sign marks the line.
2. Move the cursor into the test, and run |:DelveFrontendDebugTest|. The
   debug tab opens, and dlv builds the test and runs it to the breakpoint.
3. Step with |:DelveFrontendNext|, |:DelveFrontendStep| and
   |:DelveFrontendStepOut|, or run |:DelveFrontendContinue| to go to the
   next breakpoint.
4. Run |:DelveFrontendStop|, or close the tab, to end the session.

3. SETUP                                                *delve-frontend-setup*

						       *delve-frontend-helper*
A Go program, the helper, finds the tests in a file and drives dlv through its
JSON-RPC API. Vim starts the helper as a job on first use, and stops it when
Vim exits.

The plugin builds the helper with `go build` into `bin/delve-frontend` in the
plugin directory. It builds it when the helper starts and the binary is
missing, or older than a Go source file, `go.mod` or `go.sum` of the plugin.
On the first build, `go build` downloads delve and the other modules of the
helper.

The build runs in the background. Vim prints these messages: >
	delve-frontend: building the helper
	delve-frontend: built the helper
	delve-frontend: building the helper failed: {go build output}
<
A command that needs the helper prints this message while the build runs: >
	delve-frontend: the helper build is still running
<
After a failed build, the plugin does not build the helper again until Vim
restarts, and a command that needs the helper prints this message: >
	delve-frontend: the helper is unavailable (see :messages)
<
Every message of the plugin starts with `delve-frontend:`. When the helper
exits, the plugin prints its exit status and the lines it wrote to its
standard error.

						*delve-frontend-custom-helper*
To use a helper at another path, for example when the plugin directory is
read-only:

1. Build the helper: >
	cd /path/to/delve-frontend-vim
	go build -o ~/.local/bin/delve-frontend ./cmd/delve-frontend
<
2. Set |g:delve_frontend_helper| in your |vimrc|: >
	let g:delve_frontend_helper = expand('~/.local/bin/delve-frontend')
<
The plugin does not build a helper at another path. Build it again after
each update. When the file is missing or not executable, the plugin prints
this message: >
  delve-frontend: g:delve_frontend_helper: {path} is missing or not executable
<
						       *delve-frontend-update*
To update the plugin:

1. Update the plugin directory with your plugin manager, or with `git pull`.
2. Restart Vim, because a running Vim keeps the helper and the plugin script
   that it started with.

						*delve-frontend-uninstall*
To uninstall the plugin:

1. Remove the plugin with your plugin manager, or delete the plugin
   directory.
2. Delete a helper that you built at another path.
3. Delete the state file (see |g:delve_frontend_state_file|).

4. TESTS                                                *delve-frontend-tests*

When you enter a `_test.go` buffer, change it in Normal mode, or leave Insert
mode, the helper reads the text of the buffer, including changes not yet
written. The plugin places a sign on the first line of each test it finds.

The test at the cursor is the innermost test, subtest or table case whose
lines contain the cursor line. |:DelveFrontendRunTest| runs it with these
flags:

	Test, Fuzz, Example    `-run '^TestParse$/^empty_input$'`
	Benchmark              `-run '^$' -bench '^BenchmarkParse$'`

A pattern selects the test, its parent tests and its subtests.

						*delve-frontend-discovery*
The helper finds:

- `Test` functions that take a single `*testing.T` parameter, `Benchmark`
  functions that take a single `*testing.B`, and `Fuzz` functions that take
  a single `*testing.F`. The prefix is the whole name, or a character other
  than a lower case letter follows it: `TestParse` and `Test_parse` count,
  and `Testable` does not.
- `Example` functions without parameters that contain an `Output:` or
  `Unordered output:` comment. `go test` compiles other examples without
  running them.
- Calls to `Run` on the test's `*testing.T` or `*testing.B` parameter with a
  string literal name, or a sum of string literals, at any depth.
- Calls to `Run` in a `range` loop over a table. The helper takes the name of
  each case from one of these:
  - the loop value, in a slice, array or map of strings;
  - a field of the loop value, in a slice, array or map of struct literals,
    keyed or positional, or of pointers to them;
  - the map key, in a map.

The table is a slice, array or map literal. The literal can be in the `range`
clause, in a variable assigned before the loop in an enclosing block, or in a
package-level variable of the same file. The struct type of the entries can
be declared in any file of the package directory with the same package name.

The helper rewrites names as the `testing` package does: white space becomes
`_`, characters that do not print are escaped, and a repeated name gets the
suffix `#01`, `#02` and so on.

The helper finds only names written in the source. A case whose name the test
computes at run time, for example with `fmt.Sprintf`, gets no sign. With the
cursor in such a case, the plugin runs the parent test and all its cases.

A file that does not parse, such as one in the middle of an edit, still shows
the tests declared before the parse error.

5. DEBUG SESSIONS                                    *delve-frontend-sessions*

A debug session runs one program under dlv. Four commands start one:

	|:DelveFrontendDebugTest|   `dlv test` for the test at the cursor
	|:DelveFrontendDebug|       `dlv debug` for the main package
	|:DelveFrontendAttach|      `dlv attach` to a running process
	|:DelveFrontendConnect|     a headless dlv that is already running

Each command opens the debug tab (see |delve-frontend-tab|). Starting a
session stops the current one. dlv builds tests and main packages into a
temporary directory, and the helper removes it when dlv exits.

dlv builds with |g:delve_frontend_build_flags|. dlv and the program run with
the variables of |g:delve_frontend_env| added to the environment of Vim.

The plugin sets the saved breakpoints of the current module (see
|delve-frontend-breakpoints|), and continues the program to the first
breakpoint. A session without breakpoints runs the program to its end. To
pause a running program, run |:DelveFrontendPause|.

						*delve-frontend-stop*
|:DelveFrontendStop| and closing the debug tab end the session:

- After |:DelveFrontendDebugTest| or |:DelveFrontendDebug|, the plugin kills
  the program.
- After |:DelveFrontendAttach|, the plugin detaches, and the process keeps
  running.
- After |:DelveFrontendConnect|, the plugin clears the breakpoints it set,
  continues the program and disconnects. When dlv runs with
  `--accept-multiclient`, the program keeps running. Otherwise dlv exits when
  the plugin disconnects, and kills a program that it started.

6. BREAKPOINTS                                    *delve-frontend-breakpoints*

A sign marks each breakpoint (see |delve-frontend-highlights|). The sign
moves with the line when you edit the file.

When you set or clear a breakpoint while the program continues, the helper
halts the program, changes the breakpoint and continues the program. During
a step, the change waits until the step ends. When dlv rejects a breakpoint,
the plugin removes its sign and prints dlv's error.

|:DelveFrontendListBreakpoints| lists every breakpoint, in open files and
saved ones, in the |quickfix| list.

						*delve-frontend-state*
The plugin saves the breakpoints of each file, by absolute path, in
|g:delve_frontend_state_file|. It saves them when a breakpoint changes and
when you write a Go file, and places them again when you open the file. A
saved breakpoint after the last line of its file is dropped.

Several Vim instances can share the file. Before each write, the plugin reads
the file again. It writes only the breakpoints and watches that changed in
this Vim, and keeps the rest of the file. When the file is not valid JSON,
the plugin leaves it unchanged and prints a warning. A write that fails also
prints a warning.

Each session sets the breakpoints under the directory of the nearest `go.mod`
above the current file, or under the directory of the file when there is no
`go.mod`. The plugin loads the files of these breakpoints that are not open
into hidden buffers. It does not set breakpoints in other modules, such as
dependencies or other modules of a `go.work` workspace.

==============================================================================
7. WATCHES                                            *delve-frontend-watches*

|:DelveFrontendWatch| adds a Go expression to the watches. The plugin
evaluates each watch at every stop, and lists it at the top of the variables
pane. When a watch fails to evaluate, the plugin shows the error in place of
its value.

The plugin saves the watches in |g:delve_frontend_state_file|. Every project
shares one list of watches.

==============================================================================
8. DEBUG TAB                                              *delve-frontend-tab*

The source window fills the top of the tab. The plugin opens the file of the
selected frame there and marks the current line. At the end of each line that
uses a variable, from the start of the function to the current line, it adds
the variable's value, shortened to 60 characters.

Four panes share the bottom of the tab, |g:delve_frontend_pane_rows| lines
high. The frames and goroutines panes split that height between them:

Frames pane, at the left.
	The call stack of the selected goroutine, at most 50 frames. `→`
	marks the selected frame. The pane also shows the state of the
	session, such as `Running` or `Exited with status 0`, and errors that
	end a session. Press <Enter> on a frame to select it.

Goroutines pane, below the frames pane.
	The goroutines in groups, at most 50 groups and 10 goroutines for
	each. The first line names the grouping. Each goroutine shows its ID,
	its status, its location in every grouping except the default, and
	its pprof labels. `→` marks the selected goroutine. When the program
	stops, the selected goroutine is the one that stopped.
	With more than 5 groups, the groups without the selected goroutine
	start collapsed.
	<Enter>	On a goroutine, show its stack, with its first frame
		outside the runtime selected. The next step follows
		that goroutine. On a group, collapse or expand it.
	<Tab>	Group by the next of: the innermost frame outside the
		runtime (the default), the innermost frame, the go
		statement that started the goroutine, the function it
		started in, and a pprof label. The plugin prompts for the
		label name.
	r	Show or hide the goroutines of the runtime.

Variables pane, in the middle.
	The watches, then the arguments and local variables of the selected
	frame. The plugin loads strings up to 200 characters, and the first
	100 elements of an array, slice or map. A `(N more)` line counts the
	elements left out.
	<Enter>	Expand or collapse the variable.
	e	Ask for a Go expression, and assign its value to the
		variable.
	dd	Remove the watch.

Output pane, at the right.
	The output of dlv and of the program, from standard output and
	standard error. After |:DelveFrontendAttach| the pane shows dlv's
	output only, and after |:DelveFrontendConnect| it stays empty.

9. COMMANDS                                          *delve-frontend-commands*

						*:DelveFrontendRunTest*
:DelveFrontendRunTest
		Run the test at the cursor with `go test -json`, in the
		directory of the current file. See |delve-frontend-tests| for
		the flags. The results window at the bottom of the screen
		shows the output while the test runs. When the run ends, the
		window shows the result, the number of tests that passed,
		failed and were skipped, and the output of each failed test,
		above the full output. The sign of each test that ran shows
		its result. A run started while another runs stops the other.

						*:DelveFrontendDebugTest*
:DelveFrontendDebugTest
		Debug the test at the cursor with `dlv test`.

						*:DelveFrontendDebug*
:DelveFrontendDebug [args]
		Debug the main package in the directory of the current file,
		and pass it [args]. The helper splits [args] as a shell
		does: quotes group words, and a backslash escapes the next
		character. It expands no variables or patterns.

						*:DelveFrontendAttach*
:DelveFrontendAttach [pid]
		Attach to the running process [pid]. Without [pid], choose a
		process from a menu of the Go programs you own, highest
		process ID first. On macOS, the menu leaves out programs
		signed with the hardened runtime and without the
		`com.apple.security.get-task-allow` entitlement, because
		macOS refuses to let a debugger attach to them.

						*:DelveFrontendConnect*
:DelveFrontendConnect {host:port}
		Connect to a headless dlv listening at {host:port}, such as
		one started with this command: >
		  dlv debug --headless --accept-multiclient \
		      --listen=127.0.0.1:2345
<		Then run `:DelveFrontendConnect 127.0.0.1:2345`.

		A headless dlv does not authenticate clients. Anyone who can
		reach its port controls the program. Sessions that the plugin
		starts listen on a unix socket in a private temporary
		directory.

						*:DelveFrontendStop*
:DelveFrontendStop
		End the session. See |delve-frontend-stop|.

						*:DelveFrontendRestart*
:DelveFrontendRestart
		Start the last session again, with the build flags and
		environment of its launch, and the current breakpoints and
		watches.

					   *:DelveFrontendListBreakpoints*
:DelveFrontendListBreakpoints
		Put every breakpoint in the |quickfix| list, and open it.

					  *:DelveFrontendToggleBreakpoint*
:DelveFrontendToggleBreakpoint
		Set a breakpoint on the cursor line, or clear the breakpoint
		there.

				    *:DelveFrontendSetConditionalBreakpoint*
:DelveFrontendSetConditionalBreakpoint
		Ask for a Go expression, and set a breakpoint on the cursor
		line that stops only when the expression is true. On a line
		with a breakpoint, the prompt starts with its condition. An
		empty answer leaves the line unchanged.

						*:DelveFrontendContinue*
:DelveFrontendContinue
		Continue the program to the next breakpoint.

						*:DelveFrontendNext*
:DelveFrontendNext
		Step over to the next line.

						*:DelveFrontendStep*
:DelveFrontendStep
		Step into the call on the current line.

						*:DelveFrontendStepOut*
:DelveFrontendStepOut
		Step out of the current function.

						*:DelveFrontendPause*
:DelveFrontendPause
		Pause the running program where it is.

						*:DelveFrontendEvaluate*
:DelveFrontendEvaluate [expr]
		Show the value of the Go expression [expr] in a popup, in the
		selected frame of the selected goroutine. Without [expr],
		evaluate the expression at the cursor. To evaluate the
		selected text, use |<Plug>(delve-frontend-evaluate)| in Visual
		mode.

						*:DelveFrontendWatch*
:DelveFrontendWatch [expr]
		Add the Go expression [expr] to the watches. Without [expr],
		ask for an expression, and offer the expression at the cursor
		as the default. To add the selected text, use
		|<Plug>(delve-frontend-watch)| in Visual mode.

|:DelveFrontendDebug|, |:DelveFrontendAttach| and |:DelveFrontendConnect|.

*<Plug>(delve-frontend-next)*
	|:DelveFrontendNext|
*<Plug>(delve-frontend-step)*
	|:DelveFrontendStep|
*<Plug>(delve-frontend-step-out)*
	|:DelveFrontendStepOut|

	|:DelveFrontendPause|

	|:DelveFrontendStop|

11. OPTIONS                                           *delve-frontend-options*

						*g:delve_frontend_go*
g:delve_frontend_go		List. Default: `['go']`
	The command that runs go, as a list of words. The plugin runs it to
	build the helper and to run tests. dlv runs the go in `PATH`.

					*g:delve_frontend_build_flags*
g:delve_frontend_build_flags	List. Default: `[]`
	Build flags for |:DelveFrontendRunTest| and for dlv, such as
	`['-tags=integration', '-race']`. The plugin uses
	`b:delve_frontend_build_flags` instead, when the buffer where you run
	the command sets it.

						*g:delve_frontend_env*
g:delve_frontend_env		Dict. Default: `{}`
	Environment variables for |:DelveFrontendRunTest| and for debug
	sessions, such as `{'DATABASE_URL': 'postgres://localhost/test'}`. The
	plugin uses `b:delve_frontend_env` instead, when the buffer where you
	run the command sets it.

						*g:delve_frontend_dlv*
g:delve_frontend_dlv		String. Default: `'dlv'`
	The name or path of the dlv executable, without arguments.

						*g:delve_frontend_helper*
g:delve_frontend_helper		String. Default: `bin/delve-frontend`
				in the plugin directory
	The path of the helper. The plugin builds the helper only at the
	default path. See |delve-frontend-custom-helper|.

						*g:delve_frontend_state_file*
g:delve_frontend_state_file	String. Default:
				`$XDG_STATE_HOME/delve-frontend/state.json`,
				or `~/.local/state/delve-frontend/state.json`
	The file where the plugin saves breakpoints and watches. The plugin
	reads this variable once, the first time it needs the file.

						*g:delve_frontend_test_sign*
g:delve_frontend_test_sign	String. Default: `'▶'`
	The sign text for a test. Set it in your |vimrc|, because the plugin
	reads it only when the plugin loads.

					*g:delve_frontend_test_passed_sign*
g:delve_frontend_test_passed_sign	String. Default: `'✓'`
					*g:delve_frontend_test_failed_sign*
g:delve_frontend_test_failed_sign	String. Default: `'✗'`
	The sign texts for a test that passed or failed in its last run.
	Set them in your |vimrc|, because the plugin reads them only when the
	plugin loads.

					*g:delve_frontend_sign_priority*
g:delve_frontend_sign_priority	Number. Default: `5`
	The priority of test signs. ALE uses 30 and vim-gitgutter 10 by
	default. See |sign-priority|.

				*g:delve_frontend_breakpoint_priority*
g:delve_frontend_breakpoint_priority	Number. Default: `40`
	The priority of breakpoint signs. The current line sign uses 50.

					*g:delve_frontend_results_rows*
g:delve_frontend_results_rows	Number. Default: `15`
	The height of the results window of |:DelveFrontendRunTest|.

						*g:delve_frontend_pane_rows*
g:delve_frontend_pane_rows	Number. Default: `15`
	The height of the panes in the debug tab.

	*hl-DelveFrontendCurrentLine*      CursorLine    the current line

13. FUNCTIONS                                       *delve-frontend-functions*

					*delve_frontend#TestAtCursor()*
delve_frontend#TestAtCursor()
	Return the test at the cursor as a |Dict| with these keys, or an empty
	Dict when the cursor is outside every test:

		name       the full test name, such as `TestParse/empty_input`
		line       the first line of the test
		end_line   the last line of the test
		args       the `go test` flags that select the test, a |List|

	The result is empty until the helper has reported the tests of the
	buffer. Example, for the 'statusline': >
	  set statusline+=%{get(delve_frontend#TestAtCursor(),'name','')}
<
==============================================================================
14. LIMITATIONS                                   *delve-frontend-limitations*

- The helper does not find test methods, such as those of testify suites, or
  subtests of fuzz targets.
- The plugin has no option for test flags such as `-count`, and
  |g:delve_frontend_build_flags| is for build flags only. Repeated runs of
  an unchanged test print `(cached)` results. To run the test every time, set
  `GOFLAGS` in |g:delve_frontend_env|: >
	let g:delve_frontend_env = {'GOFLAGS': '-count=1'}
<  The go command ignores a flag in `GOFLAGS` that does not apply to it.
- |:DelveFrontendConnect| sends breakpoints with the file paths on your
  machine. A dlv in a container or on another host needs the source at the
  same paths.

15. TROUBLESHOOTING                           *delve-frontend-troubleshooting*

A session ends at once with `Exited with status 1`.
	dlv failed to build or attach. Its message is in the output pane.
	Compile errors in the test appear there.

Debugging fails with `executable file not found in $PATH`.
	Vim cannot find dlv. Add the directory of dlv to the `PATH` that Vim
	starts with, or set |g:delve_frontend_dlv| to the full path.

Attach fails on Linux.
	Many distributions let a process trace only its own children. dlv
	then prints this message in the output pane: >
	  Could not attach to pid {pid}: this could be caused by a kernel
	  security setting, try writing "0" to
	  /proc/sys/kernel/yama/ptrace_scope
<	Change that setting, or start the program with |:DelveFrontendDebug|.

Breakpoints do not stop a program after |:DelveFrontendConnect|.
	The paths of the source files differ between Vim and dlv. See
	|delve-frontend-limitations|.
